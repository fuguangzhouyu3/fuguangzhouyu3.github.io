ShareAgent 自动化用例录入指南 Help

输入、附件和变量

测试用例的输入保存在 wholeBody__c 中。输入要尽量接近真实用户表达，但不要把 企业内部不可复用的记录 ID 直接写进用户问题。通常让 Agent 看到记录名称、编号、 主题或人员名称，再在预期结果中使用变量解析后的 ID 做严格校验。

输入原则

输入内容

推荐写法

对象

使用用户可识别的对象名称或业务编号。

关联记录

使用名称、主题或自动编号；校验时通过 obj_data 取 ID。

人员

输入使用人员名称；校验字段使用人员 ID 或变量池 value。

时间

输入使用自然语言或格式化时间；校验时选择 str、yyyyMMdd 或 timestamp。

随机值

同一条用例的输入和预期结果引用同一变量。

附件

使用服务器可访问的文件路径，并提前上传文件。

文本输入

最小文本输入：

{ "user_input": "帮我查询当前企业最近一周新增的客户" }

创建场景可以使用随机客户名称，避免真实数据唯一性限制：

{ "user_input": "帮我创建一个客户，名称是${random:company}，行业是互联网" }

wholeBody__c 在 LLM 测试数据中通常以 JSON 文本保存。保存后检查最外层 JSON 可以被正常解析，且 user_input 不为空。

交互答案

当 Agent 会展示对象表单、确认问题或其他交互时，可以在输入中增加 question_answers。表单字段的 key 应使用系统返回的 input_api_name：

{ "user_input": "创建一个联系人，姓名是${random:contact_name}，手机号是${random:phone}", "question_answers": { "confirm_execution": "是", "_action": "create" } }

更新表单可以使用：

{ "user_input": "把测试联系人的手机号更新为 13800001111", "question_answers": { "confirm_execution": "是", "_action": "update" } }

_action 只在当前交互链路需要显式指定动作时使用。不要把 concel 等拼写错误 当成取消动作；取消值和字段名应以当前环境返回的交互协议为准。

卡片交互和 create_object-form 相关能力仍需按当前版本核对。若用例的目标是验证 用户交互本身，应选择当前支持的 user_interaction_form 校验方式，而不是把未完成 的卡片示例当成普通 create 用例。

附件输入

附件输入示例：

{ "user_input": "阅读我上传的附件，输出这份合同的风险", "attachment": [ { "storage_path": "/opt/data/contract-test.pdf", "filename": "contract-test.pdf", "ext": "pdf" } ] }

storage_path 是执行环境中的服务器路径，不是本地电脑的任意路径。常见约定是 把文件放在外挂目录 /opt/data/ 下：

准备文件时：

  1. 确认当前 fs-paas-test-automation 环境和对应容器。

  2. 使用环境提供的容器管理页面进入文件上传入口。

  3. 将文件上传到 /opt/data/。

  4. 用容器内的实际路径填写 storage_path。

  5. 先执行一条附件用例，确认 Agent 能读取文件，再加入批量测试集。

集群、命名空间、容器验证码和上传页面地址都属于环境配置，不要写入通用用例模板； 缺少上传权限时联系环境管理员。

context_data 自定义变量

context_data 用于承载通用的自定义上下文：

{ "context_data": { "query_instruction": { "text": "只使用 semantic-interpreter 和 object-data-query 解答以下问题：" } } }

在 user_input 中引用：

${query_instruction.text} 从线索到成单的全链路转化怎样？哪一环掉得最多？

变量路径必须与 context_data 的层级完全一致。

业务变量

业务变量适合保存当前企业的对象和人员夹具：

{ "object_data": { "AccountObj": [ { "id": "current-enterprise-account-id", "name": "当前企业测试客户" } ], "ScheduleObj": [ { "id": "current-enterprise-schedule-id", "name": "当前企业测试日程" } ] }, "employee_data": [ { "id": "current-user-id", "name": "当前测试人员", "user_name": "current_test_user", "is_current": true } ] }

不要把测试用户的 employee ID、对象 ID 或企业名称当成跨环境常量。

变量池

变量池放在 dynamic_value_pools 中，单选项使用 label/value 结构：

{ "dynamic_value_pools": { "date_single": [ { "label": "明天", "value": "${time:明天_timestamp}" } ], "employee_single": [ { "label": "当前测试人员", "value": "current-employee-id" } ], "employee_multi": [ [ { "label": "当前测试人员", "value": "current-employee-id" } ], [ { "label": "另一位测试人员", "value": "another-employee-id" } ] ] } }

输入侧通常使用 label 或 labels_joined，便于 Agent 理解；预期结果字段使用 value 或 values，便于按 ID 校验。

示例：

{ "user_input": "把当前测试日程的参与人改成${pool:employee_multi.labels_joined}" }

对应的字段校验：

{ "api_name": "participants", "display_value": "${pool:employee_multi.values}", "field_type": "employee_many", "match_mode": "contains" }

data_key 跨企业引用

data_key 是 object_data 条目上的可选逻辑标识。它让多家企业可以维护同一条用例 所需的业务对象，而每家企业保留自己的真实 ID 和名称：

{ "object_data": { "ScheduleObj": [ { "data_key": "schedule_record", "id": "enterprise-specific-schedule-id", "name": "enterprise-specific-schedule-name" } ] } }

引用方式：

${obj_data:ScheduleObj[schedule_record_id]} ${obj_data:ScheduleObj[schedule_record_name]}

data_key_id 用于预期结果的 data_id，data_key_name 用于让 Agent 看到的输入文本。 如果不使用 data_key，仍可以按当前版本支持的名称匹配方式引用，但跨企业维护时 更容易出现同名或找不到记录，建议优先使用逻辑 key。

变量排查

变量导致的失败优先检查：

  1. 变量所在层级是否为 object_data、employee_data、context_data 或 dynamic_value_pools。

  2. 对象 API 名、字段 API 名和变量池名称是否拼写一致。

  3. 当前企业是否真的存在 ID 对应的记录。

  4. 输入侧和预期侧是否引用了同一个随机变量或变量池项。

  5. 时间变量的输出类型是否与字段类型一致。
